# 后端模式切换实现方案

## 背景与调研结论

前端已把 `mode`（`plan|confirm|auto`）发送到 `POST /api/chat/agent` 的请求体（`ChatRequest.mode`）。后端在 `server/src/routes/chat.ts:156` 仅将其写入日志，**未影响图行为**。本次让三种模式真正生效。

**关键技术发现（决定方案形态）：**

1. **HITL 是编译期配置，但支持运行时覆盖。** langchain 的 `humanInTheLoopMiddleware`（deepagents 内部用它消费 `interruptOn`）在 `hitl.js:416-419` 这样读取配置：
   ```js
   const config = interopParse(contextSchema, { ...options, ...runtime.context || {} });
   ```
   即 **编译期 `interruptOn` 与运行时 `runtime.context` 合并，后者优先**。因此**一张预编译图即可**，按请求把 `interruptOn` 注入运行时 context 即可覆盖——无需为三模式预编译三张图（避免图缓存膨胀与 backend 重复构建）。

2. **运行时注入通道 = `config.context`。** 中间件消费 `runtime.context`，它对应 `agent.stream(input, { context: {...} })` 的 `context` 字段（langchain `Runtime` 类型 `runtime.d.ts:55-60` 明确 `context` 与 `configurable` 分离）。octopus 已有先例：`ConfigurableModelMiddleware` 读 `runtime.context.model`（`configurable_model.ts:23-27`）。

3. **图缓存不受影响。** mode 是 per-request 运行时数据，不进入 `_cacheKey`（`agent.ts:106-115`），无需 `clearGraphCache()`。

## 三模式语义（已与用户确认）

| 模式 | 破坏性工具 | HITL 中断 | 语义 |
|---|---|---|---|
| **plan** | **禁用**（从工具集移除） | 无（工具都没了） | 只读调研 + 输出方案，无法改动任何东西 |
| **confirm** | 可用 | **每个破坏性工具调用中断**（现状默认） | 逐步人工确认 |
| **auto** | 可用 | **全部关闭** | 全自动执行 |

破坏性工具名单（由 `_addInterruptOn()` agent.ts:271-306 与 `FILESYSTEM_TOOL_NAMES` 交叉确定）：
`write_file, edit_file, execute, task, start_async_task, update_async_task, cancel_async_task, compact_conversation`
（`web_search`/`fetch_url` 虽在 interruptOn，但属只读，plan 模式保留。）

## 改动文件（3 个）

### 1. `core/src/config.ts` — 新增 AccessMode 类型与映射

在文件顶部导出共享类型与映射表（前端已定义同名的，后端独立定义避免跨包依赖）：

```ts
export type AccessMode = "plan" | "confirm" | "auto";

/** 破坏性工具全集 — plan 模式会从工具集中移除这些。 */
export const DESTRUCTIVE_TOOLS = new Set([
  "write_file", "edit_file", "execute",
  "task", "start_async_task", "update_async_task", "cancel_async_task",
  "compact_conversation",
]);

/** mode → 运行时注入的 interruptOn 覆盖值（null 表示不覆盖，沿用编译期配置）。 */
export function interruptOnForMode(mode: AccessMode): Record<string, boolean> | null {
  if (mode === "auto") {
    // 全部置 false → 所有工具自动批准，不产生中断。
    // 覆盖编译期 _addInterruptOn() 的配置（hitl.js 行 416-419 合并语义）。
    return Object.fromEntries([...DESTRUCTIVE_TOOLS, "web_search", "fetch_url"].map((n) => [n, false]));
  }
  // plan: 工具已被移除，无需覆盖中断（没有破坏性工具可触发）。
  // confirm: 沿用编译期 interruptOn（= 全部中断），不覆盖。
  return null;
}
```

### 2. `core/src/agent.ts` — `makeGraph` 支持按 mode 过滤工具

`makeGraph` 的 `options` 增加可选 `accessMode` 字段，并在工具过滤处接入：

```ts
// makeGraph 签名 options 增加：
accessMode?: AccessMode;

// 在「2. Resolve built-in tools」之后（约 agent.ts:408 附近）新增：
if (options?.accessMode === "plan") {
  const before = tools.length;
  // plan 模式移除所有破坏性工具，agent 只能只读调研。
  const filtered = tools.filter((t: any) => !DESTRUCTIVE_TOOLS.has(t.name));
  logger.info(`plan mode: removed ${before - filtered.length} destructive tool(s)`);
  tools.length = 0;
  tools.push(...filtered);
}
```

注意：**不把 accessMode 加入 `_cacheKey`**——同一会话可能跨模式（用户中途切换），但每次 `makeGraph` 都按当时 mode 过滤工具。这里有个微妙点：图被缓存后会复用。**为避免缓存命中后用了别的 mode 的工具集**，需把 `accessMode` 加入缓存 key（否则首次以 confirm 编译的图，plan 请求会命中缓存拿到含破坏性工具的图）。

修正：`_cacheKey`（agent.ts:106-115）追加 `options?.accessMode ?? "confirm"`：
```ts
return JSON.stringify([..., mcpSignature ?? "", config.accessMode ?? "confirm" ]) + wsSignature;
```
（会带来最多 3 倍图缓存，但每张图的 backend/middleware 大部分可共享构建——可接受，且 mode 切换不频繁。）

### 3. `server/src/routes/chat.ts` — 解析 mode 并注入运行时 context + 传给 makeGraph

`/agent` 路由（chat.ts:114-221）改动：

```ts
// 1. 校验 mode（chat.ts:156 附近）
const rawMode = body.mode?.trim();
const accessMode: AccessMode =
  rawMode === "plan" || rawMode === "auto" ? rawMode : "confirm";  // 默认/非法 → confirm

// 2. 传给 makeGraph（chat.ts:170）
const compiled = await makeGraph(config, {
  cwd: agentCwd,
  workspace: { environment: workspace.environment },
  accessMode,                    // ← 新增：驱动工具过滤
});

// 3. 注入运行时 context 覆盖 HITL（chat.ts:182 langgraphConfig）
const interruptOverride = interruptOnForMode(accessMode);
const langgraphConfig = {
  configurable: { thread_id: threadId, ...(modelOverride ? { model: modelOverride } : {}) },
  // context 字段被 langchain agent 透传到 runtime.context，hitl.js 行 418 据此覆盖 interruptOn。
  ...(interruptOverride ? { context: { interruptOn: interruptOverride } } : {}),
};
```

**resume 路由（chat.ts:227-280）也要保持 mode 一致性**：HITL 中断恢复时，需用与原始请求相同的 mode。由于 mode 当前未持久化到 thread，有两个选择：

- **方案 A（推荐，简单）**：resume 时从 thread 的 langgraphConfig 继承——但 interruptOn 覆盖是运行时的、不在 checkpoint 里。实际上 resume 只在 `confirm` 模式才会发生（plan 无破坏性工具不会中断，auto 全自动不中断），所以 **resume 路由默认按 confirm 语义即可**，无需改 resume 的 langgraphConfig（保持现状 `{ configurable: { thread_id } }`）。

- 方案 B：把 accessMode 持久化到 thread 记录，resume 时读出。过度工程，当前 resume 只源于 confirm 中断，跳过。

**采用方案 A**：resume 路由不改。

## 不做的事

- **不改 tentacle 类型**：`ChatRequest.mode` 已定义（`types.ts:69`），前端已发送。
- **不改 chat.service.ts**：HITL 中断检测/恢复逻辑（`checkAndHandleInterrupts`/`streamResume`）完全复用，mode 通过运行时 context 生效，service 层无感。
- **不引入 system prompt 的 mode 引导**：用户选了"完全禁用破坏性工具"（非"禁用+提示词引导"），plan 模式靠硬性工具移除即可，不碰 `prompts.ts`。
- **不持久化 mode 到 thread**：mode 是 per-request 选择，resume 路由保持现状（见上方案 A 理由）。
- **不改前端**：前端已完整实现模式切换 UI 并发送 mode。

## 边界与风险

1. **图缓存 3 倍**：accessMode 进缓存 key 后，每种 (model,tools,shell,websearch,mcp,workspace,mode) 组合各一张图。实测 backend 构建是主要开销，但缓存命中后无额外成本。可接受。
2. **plan 模式的工具过滤位置**：必须在 MCP 工具加载（agent.ts:417）**之后**过滤，否则 MCP 注册的破坏性工具会漏网。计划在「2. Resolve built-in tools」之后的 MCP 加载块之后统一过滤——修正上面步骤 2 的位置：过滤放在 agent.ts 第 432 行（MCP 加载完成后）。
3. **configurable vs context 注入**：已验证 octopus 的 `ConfigurableModelMiddleware` 走 `runtime.context`（非 configurable），证明 `config.context` → `runtime.context` 通道在 octopus 运行时可用。model override 当前放 `configurable`（chat.ts:185）——这与 configurable_model.ts 读 `context` 似乎不一致，但那是既有的独立议题，本次不触碰 model 注入路径，只新增 `context.interruptOn`，二者不冲突。

## 验证

按 AGENTS.md，无测试 runner，用 lint 验证：

```bash
cd core && npm run lint    # tsc --noEmit
cd server && npm run lint  # tsc --noEmit
```

联调验证（server 5050 + web 5173）：
- **plan 模式**：让 agent "创建一个文件" → 应只输出方案，不出现 write_file 工具调用（或调用被拒因工具不存在）。
- **confirm 模式**：让 agent 改文件 → 弹出 HITL 批准询问（现状行为不变）。
- **auto 模式**：让 agent 改文件 → 直接执行，无中断，前端警示条显示。
- **切换验证**：同一会话先 plan 后 auto，确认行为随 mode 改变（因 accessMode 进缓存 key，会编译对应图）。
