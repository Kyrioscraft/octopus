# 用 checkpoint namespace 的 `tools:<uuid>` 作为子智能体调用实例 key

## 你提出的核心问题（已确认是关键）

子智能体 chunk 流需要区分两个维度，`lc_agent_name` 只覆盖了一个：

| 维度 | 可靠标识 | lc_agent_name 够不够 |
|---|---|---|
| 哪个子智能体**类型** | `lc_agent_name`（如 Explore） | ✅ 够 |
| **哪一次**调用 | `ns` 首段 `tools:<uuid>` | ❌ 不够——同类型多次调用会冲突 |
| 哪一轮对话 | thread_id（独立 accumulator） | ✅ 够（已隐式处理） |

## 根因诊断（基于已确认的诊断数据）

诊断实测的 ns 结构：
- 主 agent：`model_request:<uuid>`
- 子智能体：`tools:<uuid>|model_request:<uuid>` 或 `tools:<uuid>|tools:<uuid>`

**同一次子智能体调用的所有 chunk，共享同一个 `tools:<uuid>` 前缀**（诊断里固定是 `tools:e8634d1e-...`）。不同次调用 uuid 不同。所以 `tools:<uuid>` 是区分调用实例的可靠 key。

当前 Octopus 的问题：
1. **后端** `engine.ts` 只把 `lc_agent_name` 传给前端作为 `agent_ns`，**没用 `tools:<uuid>`**
2. **前端**用 `lc_agent_name` 做 SubagentEvent key，同类型多次调用会错误归并
3. 这也是 panel 为空的潜在原因之一（key 逻辑不可靠）

## 修复方案

### 改动 A：后端 `engine.ts` —— 用 `tools:<uuid>` 作为调用实例标识

改 agentNs 解析逻辑：
- 主 agent chunk（ns 首段 `model_request`）：agentNs = undefined
- 子智能体 chunk（ns 含 `tools:<uuid>`）：提取**最深层的** `tools:<uuid>` 作为调用实例 key，同时保留 lc_agent_name 作为显示名

具体：解析 ns 路径，找到 `tools:` 段，用其完整值（`tools:<uuid>`）作为 agentNs 传给前端。这样每次调用有唯一 key。

### 改动 B：后端 subagent_started 也要用同样的 key

`subagent_started` 当前用 `subagent_type`（如 general-purpose）作 agentNs。需要改成能和内部 chunk 的 `tools:<uuid>` 对应。但 subagent_started 发出时（主 agent 的 task 调用 chunk），还没有 `tools:<uuid>`（那是子图执行时才有的）。

**解法**：subagent_started 仍用一个临时 key，但当第一个带 `tools:<uuid>` 的内部 chunk 到达时，rebind 到 `tools:<uuid>`（复用已有的 rebind 机制，只是 key 换成 tools:uuid）。或者——更简单：subagent_started 不再用 agentNs 做 key，而是前端用"最近的 pending SubagentEvent"匹配（先进先出）。

### 改动 C：前端 SubagentRow 显示名

key 用 `tools:<uuid>`（实例），但**显示**用 `lc_agent_name`（类型名，如 Explore）。所以 SubagentEvent 需要**两个字段**：
- `agentNs`（实例 key，内部用）：`tools:<uuid>`
- `displayName` 或保留 lc_agent_name（显示用）："Explore"

## 待确认（需退出 plan mode 验证）

2. 嵌套子智能体（子智能体内部再调 task）时，ns 路径是否是 `tools:AAA|tools:BBB`——这种情况 deepest tools segment 是否正确对应最内层调用
3. panel 为空是否就是因为 key 不可靠（改用 tools:uuid 后是否解决）
