# TUI 滚动跳动 / 滚不下来 修复方案

## 根因总结

活跃区域（active region）每一帧的高度和宽度都不稳定，导致 Ink 高频擦除+重绘整个活跃区域，同时 `<Static>` 持续把新行推入滚动缓冲顶起视口。具体五个叠加因素：

1. **流式内容不换行 / 横向溢出**（`messages.tsx:153-166`）：`<Box flexDirection="row">` 把内容和 spinner 并排，流式 `<Text>` 没有显式宽度约束，被 spinner 挤压后不按终端宽度软换行，内容横向溢出 → 每帧重绘时行数/位置抖动。
2. **`splitIdx` 边界跳动**（`messages.tsx:515-525`）：每次 render 重新计算，tool/subagent 完成 → 消息从活跃区域迁移到 `<Static>`，把视口顶上去。
3. **spinner 每 200ms 改变字符**（`use-frame.ts` + `messages.tsx:163-165`）：每秒 5 次全活跃区域重绘。
4. **完成瞬间 `<Text>`→`<Markdown>` 重排**（`messages.tsx:156-160`）：高度剧烈变化。
5. **输入框+状态栏在 streaming 时隐藏、完成时重现**（`main-screen.tsx:151-179`）：完成瞬间活跃区域增加 3-5 行。

## 修复步骤

### 1. 修复流式内容换行 + 减少 spinner 导致的布局抖动（核心）
**文件**：`tui/src/components/messages.tsx`（`AssistantMessageView`, 152-171 行）

将流式期间的布局从 row（内容 + spinner 并排）改为 **column**：内容独占整行并显式按终端宽度换行，spinner 放在内容下方独立一行。这样：
- 内容 `<Text>` 不再被 spinner 挤压，能正确按终端宽度软换行。
- spinner 行的高度固定（1 行），不再因内容增长而位移。

具体：
- 用 `useStdout()` 取 `columns`，内容 `<Text wrap="truncate" >` 或在 column 布局下让 `flexGrow={1}` 的内层 Box 撑满宽度，Ink 的 `<Text>` 在确定宽度下会自动软换行。
- spinner 改为 `<Text color={primary}>{frame}</Text>` 独立一行，放在内容 Box 之后。
- 用 `React.useMemo` 缓存内容渲染，避免每帧重建。

### 2. 稳定 `splitIdx` 边界
**文件**：`tui/src/components/messages.tsx`（`MessageList`, 515-525 行）

引入 `useRef` 缓存上一次的 `splitIdx`，**只允许它单调递增**（只进不退）。当一个 tool/subagent 完成时，不立即把它迁移到 `<Static>`，而是等到当前活跃的 assistant 消息也 finalized 后再一起推进。这样流式过程中活跃区域的行数只在"追加"方向变化，不会因消息迁移而塌缩/顶起视口。

逻辑：
```ts
const splitIdxRef = useRef(messages.length);
// 计算新的 splitIdx（从末尾找第一个 finalized）
let newSplit = messages.length;
for (let i = messages.length - 1; i >= 0; i--) {
  if (isFinalized(messages[i]!)) { newSplit = i + 1; break; }
  newSplit = i;
}
// 只允许单调递增，避免回退导致 <Static> 反复迁移
splitIdxRef.current = Math.max(splitIdxRef.current, newSplit);
// 但当所有消息都 finalized（无活跃流式）时，允许推进到最新值
const hasActive = activeMessagesExist(messages, splitIdxRef.current);
if (!hasActive) splitIdxRef.current = newSplit;
```

### 3. 降低 spinner 重绘影响
**文件**：`tui/src/use-frame.ts`

将 `FRAME_INTERVAL` 从 200ms 调到 **300ms**（≈3.3fps），减少重绘频率。spinner 动画依然可见，但重绘次数减少 40%。配合步骤 1 把 spinner 隔离到独立行后，即便重绘也不会影响内容行。

### 4. 输入框 + 状态栏流式期间常驻
**文件**：`tui/src/components/screens/main-screen.tsx`（151-179 行）

把 `phase !== "running" && (...)` 改为始终渲染，但在 `phase === "running"` 时给 `ChatInput` 传 `disabled` 属性（只读/禁用输入），状态栏保持显示。这样完成瞬间不再有 3-5 行的突然出现。需要检查 `ChatInput` 是否已有 `disabled`/`readOnly` 支持，若无则加一个简单的禁用态（忽略按键）。

### 5. （可选）完成瞬间渲染一致性
**文件**：`tui/src/components/messages.tsx`（156-160 行）

由于步骤 2 让 finalized 的 assistant 消息在活跃区域多停留到本轮结束才进 `<Static>`，完成瞬间的 `<Text>`→`<Markdown>` 重排仍会发生一次。为彻底消除这次跳动，可以让流式期间**也使用 `<Markdown>` 渲染**（去掉 `<Text>` 分支），这样完成时只是内容停止增长，渲染器不变 → 高度只在追加方向变化。需验证 `Markdown` 组件对不完整 markdown 的容错性（从探索结果看它在 render body 里 `parseBlocks`，对不完整输入基本安全）。

> 这一项标为可选，因为它依赖 Markdown 组件对流式片段的稳定性。如果步骤 1-4 已经显著改善，可先不做。

## 验证方式

- `cd tui && npm run lint`（即 `tsc --noEmit`）确保类型正确。
- 手动运行 TUI，发起一个会触发多工具调用 + 长文本回复的请求，观察：
  - 流式内容是否正确按终端宽度换行（不再横向溢出）。
  - 工具完成时视口是否还会上跳。
  - 完成瞬间输入框/状态栏是否平滑出现（无跳动）。
  - 滚动条是否能正常滚到底部。

## 不在范围内

- 不引入应用层滚动（保持依赖终端原生滚动缓冲的设计）。
- 不改动 NDJSON 流协议或 `tui-adapter.ts` 的消息插入逻辑（`insertMessage` 行为保留）。
- 不改动 `core`/`server`/`web` 包。
