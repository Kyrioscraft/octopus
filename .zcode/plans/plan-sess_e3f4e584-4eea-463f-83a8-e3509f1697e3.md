# Skill / MCP 跨端配置抽象方案（ARCHITECTURE_PLAN 扩展章节）

> 本方案是对 ARCHITECTURE_PLAN.md 的扩展，新增"配置管理"领域的设计。落地时作为新章节（§11）追加，并对 §4 目录结构、§5 API 增补对应条目。

## 0. 问题与设计意图（来自确认）

**矛盾**：skill/mcp 的配置源真相是本地文件系统（`~/.deepagents/`、项目 `.mcp.json`），core 现有函数全部直接读写文件。tui 本地运行直读没问题；web 经 server 写入时写的是 server 机器的文件。若分离部署，两端看到不同配置。

**用户确认的设计意图**：
1. 要支持 **web/tui 配置同步**（可能分离部署）。
2. 配置来源分两类：
   - **文件源**（`.mcp.json`、`SKILL.md`、内置）→ 在 web 里**只读展示**，标记来源为"内置/文件"，不可在 web 改。
   - **web 界面创建的**（用户自定义 MCP、用户自定义 skill）→ **可增删改**，标记来源为"用户定义"。

**核心洞察**：需要一个**统一的 Store 接口**，对外透明融合"只读文件源 + 可写用户定义源"，并让可写源能跨端同步。

---

## 1. 统一的配置来源模型：`origin` 字段

所有 skill/mcp 条目统一带一个 `origin` 字段，标识来源，决定可写性：

```ts
type SkillOrigin = "builtin" | "file" | "user-defined";
type McpOrigin   = "file" | "user-defined";

interface SkillEntry extends SkillMetadata {
  origin: SkillOrigin;        // builtin/file → 只读; user-defined → 可增删改
  editable: boolean;          // = (origin === "user-defined")
  description: string;
  // file/builtin 源额外带 path/source；user-defined 源带存储 id
}

interface McpServerEntry {
  name: string;
  origin: McpOrigin;
  editable: boolean;
  transport: "stdio" | "sse" | "http" | "streamable-http";
  config: Record<string, unknown>;   // command/args/env 或 url 等
  enabled: boolean;                   // 禁用状态（复用现有 setServerDisabled）
  status?: MCPServerStatus;           // 连接状态（仅 list 时实时探测填充）
}
```

**规则**：
- `origin === "file" | "builtin"` → `editable: false`，web/tui 只展示，改它要去改对应文件。
- `origin === "user-defined"` → `editable: true`，可经 API 增删改。
- 同名时优先级：`user-defined > file > builtin`（与现有 skills 的"高优先级覆盖低优先级"一致）。

## 2. 三层职责划分

```
core:   SkillStore / McpStore 接口
        ├─ FileSource      (只读: 复用现有 listSkills/loadMcpConfig/discoverMcpConfigs)
        └─ UserDefinedStore(可写: 新增, 落在 server DB)
server: routes/config.ts   → 薄 HTTP 适配, 调 store
        db/schema.ts       → 新增 user_skills / user_mcp_servers 表
tui:    直接读文件源(本地) + 经 HTTP 读 user-defined 源(同步)
web:    全部经 HTTP(它碰不到文件)
```

### 关键决策：user-defined 源存 DB，不存文件

理由（基于"要支持分离部署 + 同步"）：
- 存本地文件 → web 写的是 server 机器的文件，分离部署时 tui 在本地看不到 → 同步失败。
- 存 server DB → web 经 server 读写 DB，tui 经 HTTP 读同一份 DB → **天然同步**。
- 文件源保持只读不动（tui 本地直读，web 经 server 读），DB 是唯一的"user-defined 真相源"。

## 3. core 层：SkillStore / McpStore 接口

### 3.1 接口定义（`core/src/config_store.ts` 新增）

```ts
/** 统一的配置读取接口 — server 和(未来)tui 都依赖这个契约 */
export interface SkillStore {
  list(): Promise<SkillEntry[]>;                              // 合并 file + user-defined
  get(name: string): Promise<SkillEntry | null>;
  create(input: { name; description; content }): Promise<SkillEntry>;   // 仅 user-defined
  update(name: string, patch: { description?; content? }): Promise<SkillEntry>;
  remove(name: string): Promise<void>;                        // 仅 user-defined
}

export interface McpStore {
  list(opts?: { probe?: boolean }): Promise<McpServerEntry[]>;  // 合并 file + user-defined, probe=实时探测连接
  get(name: string): Promise<McpServerEntry | null>;
  create(input: { name; transport; config }): Promise<McpServerEntry>;
  update(name: string, patch): Promise<McpServerEntry>;
  remove(name: string): Promise<void>;
  setEnabled(name: string, enabled: boolean): Promise<void>;    // 复用现有 setServerDisabled 语义
}
```

### 3.2 两个 Source 实现

**FileSource（只读，复用现有函数）**：
- `listSkills()` / `loadMcpConfig()` / `discoverMcpConfigs()` / `mergeMcpConfigs()` 原样复用，只是给结果加 `origin: "file"|"builtin"`、`editable: false` 标记。
- **不改现有文件读写逻辑**，纯粹是"在现有只读发现之上包一层 origin 标记"。

**UserDefinedStore（可写，依赖 DB）**：
- core 定义 `UserDefinedStoreBackend` 接口（`getall/upsert/delete`），**不直接依赖 better-sqlite3**（保持 core 零 DB 依赖的原则）。
- server 提供该接口的 DB 实现（`server/src/services/config-store.db.ts`），注入给 core 的 store。
- 这保持 core 的环境无关性（和 AGENTS.md 的"core 无 DB"原则一致），具体 DB 落在 server。

### 3.3 合并逻辑（list 时）

```
list():
  1. fileEntries = FileSource.list()        // 现有文件发现
  2. userEntries = UserDefinedStore.list()  // DB 读
  3. 按 name 合并: user-defined 覆盖同名 file/builtin
  4. 返回带 origin/editable 标记的统一列表
```

### 3.4 现有函数的去留

- `listSkills` / `loadMcpConfig` / `discoverMcpConfigs` → **保留**，作为 FileSource 的内部实现，`index.ts` 继续导出（tui 直读文件仍可用）。
- `setServerDisabled` / `trustProjectMcp` 等 → **保留**，`setEnabled` 内部复用它们处理"禁用/信任"状态（禁用状态仍写 `config.json`，因为它是运行时状态而非配置定义）。
- `generateSkillTemplate` → **保留**，`create` 时用来给用户生成初始模板。
- 新增 `createSkill` / `deleteSkill` 落盘逻辑参考内置 `init_skill.ts`，但写到 user-defined store（DB）而非文件。

## 4. server 层：新增 config 领域

### 4.1 目录与路由

```
server/src/
├── routes/
│   └── config.ts              # 【新】GET/POST/PUT/DELETE /api/config/skills, /api/config/mcp
├── services/
│   ├── skill.service.ts       # 【新】编排 SkillStore
│   └── mcp.service.ts         # 【新】编排 McpStore (list 带 probe 时调 resolveAndLoadMcpTools 探测状态)
└── services/
    └── config-store.db.ts     # 【新】UserDefinedStoreBackend 的 DB 实现
```

### 4.2 DB 新增表（`server/src/db/schema.ts`）

```ts
export const userSkills = sqliteTable("user_skills", {
  id: text("id").primaryKey(),
  userId: text("user_id").notNull(),
  name: text("name").notNull(),
  description: text("description").notNull(),
  content: text("content").notNull(),          // SKILL.md 全文
  createdAt: text("created_at").notNull(),
  updatedAt: text("updated_at").notNull(),
}, (t) => ({ uniq: uniqueIndex("us_user_name").on(t.userId, t.name) }));

export const userMcpServers = sqliteTable("user_mcp_servers", {
  id: text("id").primaryKey(),
  userId: text("user_id").notNull(),
  name: text("name").notNull(),
  transport: text("transport").notNull(),
  config: text("config").notNull(),            // JSON
  createdAt: text("created_at").notNull(),
  updatedAt: text("updated_at").notNull(),
}, (t) => ({ uniq: uniqueIndex("um_user_name").on(t.userId, t.name) }));
```

按 `userId` 隔离（多用户场景），unique 约束防同名。

### 4.3 agent 运行时接线（`makeGraph` / `AgentEngine.resolve`）

现有 `agent.ts` 加载 skill/mcp 的地方，改为从 `SkillStore` / `McpStore` 的 `list()` 结果取合并后的全集（file + user-defined），而不是只读文件源。这样 **web 创建的 user-defined skill/mcp 能立即被 agent 使用**。

## 5. API 设计

### 5.1 Skills（基础接口性质——所有 UI 共用）

| 方法 | 路径 | 功能 | 写权限 |
|---|---|---|---|
| `GET` | `/api/config/skills` | 列出所有 skill（file+builtin+user-defined，带 origin/editable） | 只读 |
| `GET` | `/api/config/skills/:name` | 查看 skill 内容 | 只读 |
| `POST` | `/api/config/skills` | 创建 user-defined skill | 仅 user-defined |
| `PUT` | `/api/config/skills/:name` | 更新（仅 user-defined 可改） | 仅 user-defined |
| `DELETE` | `/api/config/skills/:name` | 删除（仅 user-defined 可删） | 仅 user-defined |

对 file/builtin 源的 skill 做 POST/PUT/DELETE → 返回 `409 {error:"not_editable", origin:"file"}`，提示"该 skill 来自文件，请直接编辑文件"。

### 5.2 MCP（同理）

| 方法 | 路径 | 功能 |
|---|---|---|
| `GET` | `/api/config/mcp` | 列出所有 MCP server（带 origin/enable/status），`?probe=true` 实时探测连接 |
| `POST` | `/api/config/mcp` | 创建 user-defined MCP server |
| `PUT` | `/api/config/mcp/:name` | 更新（仅 user-defined） |
| `DELETE` | `/api/config/mcp/:name` | 删除（仅 user-defined） |
| `PUT` | `/api/config/mcp/:name/enabled` | 启用/禁用（任意 origin 都可，复用 setServerDisabled） |

### 5.3 为什么不归入 §5.2 的 `/ext/*`

skill/mcp 配置是 **web 和 tui 都需要的基础能力**（tui 也要列 skill、看 mcp 状态），不是 web 特有的扩展功能（如附件上传）。所以放 `/api/config/*` 作为独立的基础资源域，而非 `/ext/*` 扩展。与 §5.3 决策一致——这里没有用能力探测，只是按资源域分组。

## 6. tui 的兼容接入（关键）

tui 有两条数据路径，自然兼容：

1. **文件源**（builtin/file）→ tui 仍直接 `import @octopus/core` 的 `listSkills`/`loadMcpConfig` 读本地文件（快、离线可用）。
2. **user-defined 源**（DB）→ tui 经 HTTP（tentacle client 新增 `listSkills()`/`listMcp()` 方法）读 server DB，实现与 web 同步。

**tui 的合并视图**（在 `tui/src/components/` 新增或扩展）：
- 本地文件源 + HTTP user-defined 源各拉一份，按 name 合并（user-defined 优先），展示带 origin 标记。
- 若 server 不可达，降级为仅本地文件源（tui 的离线韧性）。

**tui 的写入**：
- tui 不直接写 user-defined（避免绕过 server 导致不同步）——若 tui 要创建 skill/mcp，也经 HTTP POST 到 server，和 web 走同一条路。
- 文件源仍由用户手动编辑文件（tui 定位就是面向开发者，手改文件是常态）。

这样 **web 和 tui 对 user-defined 配置永远一致**（都读写同一份 server DB），文件源各读各的本地（同机时一致，分离时各自展示本地文件，符合预期）。

## 7. tentacle 层补强

`OctopusClient` 新增 config 领域方法（基础接口，非 ext）：

```ts
class OctopusClient {
  skills: {
    list(): Promise<SkillEntry[]>;
    get(name): Promise<{ content: string; origin: SkillOrigin }>;
    create(input): Promise<SkillEntry>;
    update(name, patch): Promise<SkillEntry>;
    remove(name): Promise<void>;
  };
  mcp: {
    list(opts?: { probe?: boolean }): Promise<McpServerEntry[]>;
    create(input): Promise<McpServerEntry>;
    update(name, patch): Promise<McpServerEntry>;
    remove(name): Promise<void>;
    setEnabled(name, enabled): Promise<void>;
  };
}
```

`tentacle/src/types.ts` 补 `SkillEntry` / `McpServerEntry` / `SkillOrigin` / `McpOrigin` 类型（web/tui 共享）。

## 9. 兼容性与边界

| 场景 | 行为 |
|---|---|
| web 改不了文件源 skill | API 返回 409 + origin 标记，UI 灰显编辑按钮，提示"来自文件" |
| tui 离线（server 不可达） | 降级为仅本地文件源，user-defined 列表为空，不报错 |
| 同名 file + user-defined | user-defined 覆盖展示；agent 加载时取 user-defined 版本 |
| 分离部署 | user-defined 经 DB 同步（web/tui 读同一份）；文件源各端读各本地（符合预期） |
| 禁用状态 | 任意 origin 的 server 都可禁用（写 config.json，运行时状态），不改源定义 |

## 10. 不做的事

- 不让 web 直接编辑文件源（保持文件源只读，避免 web 写 server 机器文件造成混乱）。
- 不把文件源同步进 DB（文件源是各端本地的，DB 只存 user-defined）。
- 不引入文件变更监听（file 源的变更靠重启或手动刷新 list 感知，不做 watch）。
- 暂不做 user-defined 的版本/历史（简单 upsert 即可）。
