# Web 模型配置修复计划

## 背景与根因总结

用户反馈两个问题，经过代码溯源已定位根因：

### Bug #1：无法添加全新供应商
- **现象**：设置页只能看到注册表里的固定供应商，无法手动添加自定义供应商（如自建的 OpenAI 兼容代理）。
- **根因**：前端 `ModelSettingsSection.tsx` 只有"搜索供应商"框，**没有"添加供应商"入口按钮**。后端 `PUT /api/config/models/:name` + `saveProviderConfig` 其实已支持新建 provider（`providers[name] ?? {}`），只缺前端 UI。
- **附带问题**：`listProvidersOverview()` 把 `PROVIDER_API_KEY_ENV` 注册表里 **19 个**供应商全部列出来，即使没任何配置，用户觉得太多。

### Bug #2：填入的 URL 没生效
- **现象**：在「配置」弹窗里改了 Base URL，写入了 config.json，但对话仍走旧 URL。
- **根因**（精确版）：`makeGraph` 用 `_graphCache` 永久缓存编译好的 graph。graph 编译时（`_makeGraphUncached`）调 `_buildChatModel(config.model, ...)` 创建了一个**初始模型实例**，其 baseURL 被固化进 `ChatOpenAI`/`ChatAnthropic` 实例。当用户用**默认模型**发消息时（`selectedModel === null` → 无 `modelOverride`），`ConfigurableModelMiddleware` 不会触发重建（第 28 行 `if (modelSpec && ...)` 不成立），于是实际调用的就是那个带旧 baseURL 的初始实例。`clearGraphCache` 已导出但**全项目无人调用**。
- **用户期望的修复方式**：在对话输入**选择新模型时**清缓存（按需失效），而非保存配置时全量清。

## 改动清单

### 改动 1：精简注册表为常用供应商（core）
**文件**：`packages/core/src/constants.ts`（`PROVIDER_API_KEY_ENV` 第 23-43 行、`PROVIDER_BASE_URL_ENV` 第 51-68 行）

把 19 个供应商精简为常用的 6 个：`anthropic`、`openai`、`deepseek`、`openrouter`、`ollama`、`xai`。
- 删除：`azure_openai`、`baseten`、`cohere`、`fireworks`、`google_genai`、`google_vertexai`、`groq`、`huggingface`、`ibm`、`litellm`、`mistralai`、`nvidia`、`perplexity`、`together`。
- `PROVIDER_BASE_URL_ENV` 同步精简，只保留对应的 6 个。
- `listProvidersOverview` 逻辑不变（它遍历注册表 + config.json 已有的），所以**用户之前在 config.json 里自定义的 provider 仍然会显示**——只是注册表里的模板少了。这也意味着"内置"= 在精简后注册表里的，"自定义"= 不在注册表里的。

> 注意：删掉的供应商若用户之前在 config.json 里已有配置，仍会通过 `listProvidersOverview` 第二个循环（第 328 行）显示出来，不会丢数据。

**文件**：`packages/web/src/components/settings/ModelSettingsSection.tsx`

- 在「模型供应商」Card 的 `extra` 区域（第 146-155 行，目前是搜索框）旁边加一个「添加供应商」按钮（`<Button icon={<Plus />}>添加供应商</Button>`）。

### 改动 4：对话选择模型时按需清缓存（server + core）
**这是 Bug #2 的核心修复**，按用户要求"在对话输入选择新的模型后清除图缓存"。

**方案**：当 chat 请求带有 `modelOverride`（用户在对话输入选了非默认模型）时，先清 graph 缓存再 `makeGraph`，确保重建时读到最新 config.json。

- **server** `packages/server/src/routes/chat.ts`（第 227-259 行附近）：
  - 引入 `clearGraphCache`（从 `@octopus/core`，已导出）。
  - 在 `const modelOverride = body.model?.trim() || undefined;`（第 228 行）之后，加：
    ```ts
    if (modelOverride) {
      // 用户在对话输入选择了非默认模型，清除 graph 缓存确保
      // 重建时读取最新的 config.json（含最新 baseURL/apiKey）。
      clearGraphCache();
    }
    ```
  - 同时在文件顶部 `import { ..., clearGraphCache } from "@octopus/core";`（确认 `@octopus/core` 已导出，见 `index.ts:6` 附近，需检查 `clearGraphCache` 是否在导出列表中；若无需补导出）。

**为什么只在 `modelOverride` 时清**：
- 用默认模型时 graph 复用缓存是 OK 的（默认模型本身没变）。
- 用户主动切换模型 = 明确的"我想用新配置"信号，此时清缓存重建，新的 `_buildChatModel` 会实时读 config.json 的最新 `getBaseUrl()`，新 URL 生效。
- 避免了"每次请求都重建 graph"的性能损耗。

> 补充：`loadConfig()`（chat.ts:227）已经调了 `clearCaches()`（清 `_configCache` 读缓存），所以重建时读的是最新文件。这条链路是通的，只差 graph 缓存这层。

### 改动 5：确认 `clearGraphCache` 已从 core 导出（core）
**文件**：`packages/core/src/index.ts`

检查 `clearGraphCache` 是否在导出列表中。若未导出，添加 `export { clearGraphCache } from "./agent.js";`。（探索报告显示它在 `agent.ts:123` 定义，需确认 `index.ts` 是否已 re-export。）

## 不改动的部分
- `loadConfig` 里 `providerOverrides` 始终为空的设计——不在本次修复范围内（治本但改动大，且改动 4 已能解决 URL 生效问题）。
- `_cacheKey` 不纳入 baseURL——用户明确要求"选择模型时清缓存"，而非改 key 逻辑。
- 后端 `saveProviderConfig` 逻辑——已经正确，无需改。
- resume 路径不带 model override——保持现状（本次不改 resume 流程）。
